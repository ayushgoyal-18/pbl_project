PUF MedAuth

A Hybrid Pharmaceutical Authentication Framework

Combining QR serialization with a cryptographically bound, software-generated optical fingerprint to authenticate pharmaceutical packages using ordinary camera images.

01 • Motivation

The Problem

Why QR Alone Is Not Enough

A QR code is excellent for serialization and identifying a product or package, but a visible QR code can be photographed, copied and reproduced. Therefore, possession of the same public identifier does not by itself prove that the presented package corresponds to the enrolled reference.

Public identifier

Useful for serialization

Easy to reproduce

Copying remains possible

Project Objective

Develop a low-cost, software-controlled authentication mechanism where a copied public serialization value is insufficient to directly reproduce the enrolled Version-2 optical reference, while verification remains practical from ordinary package photographs.

02 • Proposed Framework

How PUF MedAuth Works

The system separates public package serialization from the secret-bound optical authentication signal.

Step 01

Package Enrollment

Product metadata and a package-specific authentication identifier are registered in the reference database.

Step 02

Cryptographic Binding

Product ID and the unique Package Auth ID are bound to a server-held secret through HMAC-SHA256.

Step 03

Optical Fingerprint

A deterministic 200 × 200 intensity pattern is generated from the derived seed, smoothed, normalized and placed on the printable label.

Step 04

Camera Verification

The uploaded image is normalized, rectified and compared against the enrolled optical reference before the final authentication decision.

04 • Security Upgrade

Version 2 Cryptographic Binding

The major upgrade over the legacy Version-1 design is the introduction of package-specific, secret-bound fingerprint derivation.

128-bit Package Auth ID

Each Version-2 package receives an independently generated 128-bit authentication identifier represented as 32 hexadecimal characters.

HMAC-SHA256

The Product ID and Package Auth ID are combined and processed using a server-held secret as the HMAC key. The secret is not placed in the QR code.

Public / Secret Separation

Public package data is separated from the secret used for Version-2 derivation, reducing direct offline regeneration from the visible serialization fields.

Version-2 derivation

Message

Product ID | Package Auth ID

Secret key

Server-held HMAC secret

HMAC-SHA256 → deterministic seed → seeded PRNG

200 × 200 intensity matrix → Gaussian smoothing → normalization → printable optical fingerprint

Security claim is deliberately limited: Version 2 makes direct mathematical regeneration from only public Product ID + Auth ID impractical without the server-held secret. It does not claim physical unclonability of a printed image.

05 • Authentication Engine

Robust Optical Verification

Image Normalization

EXIF correction

Smartphone JPEG orientation is normalized before computer-vision processing.

Marker-constrained localization

QR finder squares are not treated as the fingerprint fiducials.

Perspective rectification

The detected package region is mapped to canonical geometry before fingerprint extraction.

Multi-Stage Comparison

NCC Primary

Evaluated at 10 spatial resolutions and 4 orthogonal orientations. The best valid value is retained.

06 • Decision Model

Four Explicit Outcomes

GENUINE

A valid enrolled reference satisfies the authentication decision rule.

COUNTERFEIT

A known product fails the optical authentication check.

NO_MATCH

Blind 1:N search finds no enrolled reference satisfying the decision rule.

UNABLE_TO_AUTHENTICATE

The image cannot be reliably processed; it is not automatically labelled counterfeit.

07 • Engineering Validation

What Has Been Tested

The current project includes a dedicated Version-2 security and compatibility validation suite. These are engineering tests, not a statistically representative field-accuracy study.

Deterministic derivation

Same Product ID + Auth ID + secret produces the same Version-2 fingerprint.

Input sensitivity

Changing Product ID, Auth ID or secret changes the generated fingerprint.

QR security checks

V2 QR fields round-trip correctly and the server secret is absent from the QR payload.

Wrong-match rejection

Wrong Product ID, unrelated patterns and cross-version presentations are rejected in the test suite.

Secret leakage checks

Verification JSON and public HTML responses are checked for absence of the server secret.

19 / 19 predefined Version-2 validation tests passed

This demonstrates implementation-level consistency of the tested mechanisms. It is not a claim of 100% real-world accuracy or resistance to every physical reproduction attack.

08 • Research Contribution

From Prototype to Research

Research Gap Addressed

  • • QR/2D serialization identifies packages but does not independently authenticate the optical reference.
  • • Physical PUF approaches can require specialized materials, readers or manufacturing processes.
  • • Optical authentication must tolerate ordinary camera capture, orientation, perspective, printing and resampling effects.
  • • Evaluation needs to distinguish engineering validation from statistically meaningful field accuracy.

Key Technical Contribution

  • 01. Per-package 128-bit authentication identifier.
  • 02. Product ID + Auth ID binding through server-held HMAC-SHA256.
  • 03. Printable software-generated optical fingerprint.
  • 04. Marker-constrained geometric normalization.
  • 05. Multi-scale / multi-orientation NCC with secondary ORB/RANSAC evidence.
  • 06. NCC safety floor and explicit failure states.

10 • Critical Evaluation

Limitations & Future Scope

Current Limitations

  • • A visible software-generated optical token can still be photographed and potentially reproduced.
  • • The current validation suite is engineering-focused rather than a large field study.
  • • Real-world performance needs broader testing across printers, substrates, cameras, lighting, curvature and deliberate reproductions.
  • • Threshold values are implementation parameters and are not claimed to be universally optimal.

Next Development Steps

  • • Build a larger, independently collected physical-package dataset.
  • • Evaluate multiple printers, papers, cameras, lighting conditions and package curvatures.
  • • Perform ablation studies: NCC-only, ORB-only, fused model and gated model.
  • • Report confusion matrix, ROC/PR analysis and threshold sensitivity.
  • • Investigate stronger anti-replay and print/copy-channel characterization.
  • • Continue formal patentability and claim analysis with professional counsel.
